# The dataset, the features actually used, and how satellite imagery feeds the models

This file exists so the answer to *"what did you actually build the models
from, and how does the satellite-image part of the problem statement show
up in code"* is visible directly in the repo, without having to run
anything. Two small, real samples are committed alongside this doc:

- **[`synthetic/sample_dataset.csv`](synthetic/sample_dataset.csv)** — 25 rows, straight out of
  `synthetic.ocean_pipeline_demo.build_training_table()`, unmodified except
  rounding for readability. This is exactly what every synthetic-track
  model trains on.
- **[`real/sample_dataset.csv`](real/sample_dataset.csv)** — 25 rows, straight out of
  `real.real_training.build_real_training_table()`, same treatment. This is
  exactly what every real-data-track model trains on (see
  `real/PROVENANCE.md` for where the underlying MOSDAC/CMEMS files came
  from).

Both are small enough to open directly on GitHub and scroll through — that
is the point of committing them, rather than only describing the schema in
prose.

## 1. The problem statement's 5 required surface inputs, vs. what's actually used

| Required input | Synthetic track | Real track |
|---|---|---|
| SST | `sst` — synthetic formula | `sst` — real, CMEMS `thetao` |
| SSS | `sss` — synthetic formula | `sss` — real, CMEMS `so` |
| SSH / SLA | `ssh` — synthetic Gaussian "eddy" field | **not available** — no real altimetry file obtained |
| Surface currents (U, V) | not modeled (no synthetic current field) | `uo`, `vo` — real, CMEMS |
| Surface winds (U, V) | `u_wind`, `v_wind` — synthetic, plus a derived `curl` field | **not available** — no real wind product obtained |

Two tracks exist specifically because real data doesn't yet cover all 5
inputs (see `real/PROVENANCE.md` for exactly which files exist and what's
missing) — the synthetic track fills every input with a physically-motivated
formula so the full model comparison could run end-to-end regardless.

## 2. Feature selection: every candidate field vs. what each model type actually consumes

`get_satellite_grid()` (synthetic) produces 9 fields; the real pipeline's
loaders produce 7. Not every field is fed to every model — two different
"relevant feature" subsets exist because the tabular models and the
satellite-patch models consume the data differently:

| Field | In synthetic grid? | In real data? | Used by tabular models (`FEATURE_COLS` / `REAL_FEATURE_COLS`) | Used by CNN/ViT satellite patch (`PATCH_CHANNELS` / `PATCH_CHANNELS_REAL`) |
|---|:-:|:-:|:-:|:-:|
| `lat`, `lon` | yes | yes | yes | — (used to *locate* the patch, not as a channel inside it) |
| `day` | yes | yes | yes | — (concatenated after the patch embedding, not spatial) |
| `sst` | yes | yes | yes | yes |
| `ssh` | yes | no | yes (synthetic only) | yes (synthetic only) |
| `sss` | yes | yes | yes | yes |
| `wind` (scalar speed) | yes | no | superseded by `u_wind`/`v_wind`/`curl` below | no |
| `u_wind`, `v_wind` | yes | no | yes (synthetic only) | no (only `curl` derived from them enters the patch, see below) |
| `curl` (derived) | yes | no | yes (synthetic only) | yes (synthetic only) |
| `uo`, `vo` (currents) | no | yes | yes (real only) | yes (real only) |
| `cluster_0..5` (derived) | yes | no | yes, one-hot (synthetic only) | no |

**Why `curl` and not raw wind in the patch:** `compute_wind_stress_curl()`
derives Ekman-pumping-relevant curl from `u_wind`/`v_wind` (central finite
differences, cos(lat)-weighted) — this is the specific extra input Xie et
al. 2022's Attention U-Net paper found to be the single biggest accuracy
lever below ~50 m. It replaced the redundant scalar `wind` field in
`PATCH_CHANNELS` because `sst/ssh/sss/curl` carries more distinct spatial
information than `sst/ssh/sss/|wind|` did — verified on this repo's own
data (README §"The models").

**Why the real feature set is smaller (7 vs 16 columns):** only SST, SSS,
and surface currents have a real source at all — no real wind or SSH/SLA
file exists yet, so `real/real_training.py`'s `REAL_FEATURE_COLS` and
`PATCH_CHANNELS_REAL` simply omit them rather than mixing in a synthetic
stand-in. See `PROJECT_REPORT.txt` §1a item 3 for the full reasoning.

The cluster one-hot columns (`cluster_0`..`cluster_5`) come from
`spatiotemporal_clusters()` — a KMeans pass over `(lat, lon, day, ssh)`,
inspired by Loo et al. 2026's adaptive clustering framework — and are
tabular-model-only, not part of the satellite patch.

## 3. How satellite imagery specifically is used (the "compact embedding" requirement)

The problem statement asks for "compact satellite embeddings" generated by
a CNN, ViT, Autoencoder, GNN, or attention-hybrid. The CNN and ViT are
literally that: each reads a real spatial crop of the satellite grid, not a
single point value.

```
Satellite grid for day D                Profile at (lat, lon), day D
(full basin, every 1.0 deg cell,   ---->  find nearest grid cell (i, j)
 4 channels: sst/ssh/sss/curl)            extract a 5x5 neighborhood
                                           around (i, j), edge-replicated
                                           padding at basin boundaries
                                                    |
                                                    v
                                   patch: shape (4 channels, 5, 5)
                                                    |
                          -------------------------------------------------
                          |                                               |
                          v                                               v
                   CNN (PatchCNN)                                  ViT (PatchViT)
             Conv2d(3x3) -> ReLU                          each of the 25 cells = 1 token
             Conv2d(3x3) -> ReLU                          linear projection + learned
             GlobalAvgPool                                positional embedding per token
                          |                          1 TransformerEncoder layer (self-attention)
                          v                                mean-pool over tokens (no CLS)
             32-dim embedding vector                                       |
                          |                                                v
                          |                                    embedding vector
                          -------------------------------------------------
                                                    |
                                    concat with `day` (non-spatial)
                                                    |
                                                    v
                                    small regression head
                                                    |
                                                    v
                              predicted temperature at 15 standard depths
```

`extract_patch()` (`models/dl_pipeline.py`) is the single function that
builds this crop, shared identically by both the CNN and the ViT — so the
CNN-vs-ViT comparison in the Results tab isolates "convolution vs.
attention" as the only variable, not "different input data too." The real
track uses the exact same mechanism (`build_real_patches()` in
`real/real_training.py`) with real `sst/sss/uo/vo` channels instead of the
synthetic `sst/ssh/sss/curl`.

This is the most literal reading of "satellite embedding" in this repo: a
compact latent vector produced *from a spatial image patch*, as opposed to
the tabular models (FFNN, Random Forest, GNN, Autoencoder, LSTM), which
read the same location as a flat list of numbers with no spatial context
at all. Full architecture-by-architecture detail (exact layer shapes, why
ViT edged out CNN, why GNN needed a skip connection) is in
`PROJECT_REPORT.txt` §1c section E and §2 item 4.
