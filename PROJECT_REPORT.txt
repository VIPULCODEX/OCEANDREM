1. THE ACTUAL PROBLEM STATEMENT (as given by the user, summarized faithfully)
--------------------------------------------------------------------------------
Build a "Satellite Embedding-Based Deep Learning Framework" that reconstructs
depth-wise subsurface ocean temperature from daily surface satellite
observations, at 0.25 deg spatial resolution, for the North Indian Ocean
(5N-30N, 45E-105E).

Required system components:
  1. Preprocessing/harmonization pipeline for multi-source satellite + ocean
     datasets.
  2. Standardize all datasets to: 0.25 deg x 0.25 deg spatial, DAILY temporal.
  3. Input variables (surface only):
       - SST  (Sea Surface Temperature)
       - SSS  (Sea Surface Salinity)
       - SSH / SLA (Sea Surface Height / Sea Level Anomaly)
       - Surface currents (U, V)
       - Surface winds (U, V)
  4. Generate COMPACT SATELLITE EMBEDDINGS using a deep-learning architecture:
       CNN, Vision Transformer, Autoencoder, GNN, or attention-based hybrid.
  5. Train a reconstruction model: surface state -> temperature profile.
  6. Reconstruct temperature at standard depths (meters):
       0, 5, 10, 20, 30, 50, 75, 100, 125, 150, 200, 300, 500, 700, 1000
  7. Evaluate with independent observations + standard skill metrics
     (correlation, RMSE, bias, etc.). If a dataset isn't available at the
     required resolution, pick an open product and interpolate/regrid.

Recommended datasets:
  - Target (subsurface temperature): GLORYS Global Ocean Reanalysis
    (https://doi.org/10.48670/moi-00021), variable = Temperature.
  - Validation: In-situ Gridded ARGO, via INCOIS Live Access Server (LAS).

Expected deliverables:
  - End-to-end preprocessing pipeline.
  - Satellite embedding engine (DL, latent ocean representations).
  - DL reconstruction model for subsurface temperature.
  - Standardized daily, 0.25 deg output.
  - Validation framework using independent ARGO obs.
  - Working PoC demo over the Bay of Bengal / Arabian Sea.


2. HONEST STATUS: WHAT'S ACTUALLY BUILT VS. THE SPEC
--------------------------------------------------------------------------------
This was built in a ~2 hour sprint with a hard deadline, starting from an
already-existing synthetic RandomForest demo. Priorities were: (a) get a
working, honest, presentable end-to-end demo up, (b) integrate whatever real
data the user could actually get their hands on in the time available,
(c) don't fake results. Below is a component-by-component grade against the
spec. Read this section before telling anyone the project is "done".

  [PARTIAL] 1. Preprocessing/harmonization pipeline
      - real_data.py reads real MOSDAC (.h5, INSAT-3DR SST) and real CMEMS
        (.nc, thetao + so) files, resolves files by the variable they
        contain (robust to browser-renamed filenames), masks fill values,
        applies scale/offset, crops to the study region, and computes
        daily aggregates.
      - This is a real but MINIMAL harmonization step. It does NOT do
        general multi-source regridding (e.g. reprojecting MOSDAC's native
        geostationary swath grid onto the same lat/lon grid as CMEMS), and
        there is no unified "one pipeline, N input products" abstraction --
        each source has its own bespoke loader function.
      - ocean_pipeline_demo.py's synthetic side has no harmonization step at
        all since it generates already-aligned synthetic fields directly.

  [NOT DONE] 2. Standardize to 0.25 deg spatial / daily temporal
      - CMEMS real data is natively 0.083 deg, 6-hourly -- we resample to
        DAILY (mean) for the real time series, but we never regrid the
        0.083 deg grid up to 0.25 deg. The exported map "snapshot" grid is
        just a strided (coarsened) view of the native grid, not a proper
        0.25 deg regrid (no interpolation, just decimation).
      - MOSDAC is native swath resolution (~4 km at nadir, geostationary
        projection), also just decimated by pixel stride, not regridded to
        a regular 0.25 deg lat/lon grid.
      - The synthetic pipeline (ocean_pipeline_demo.py) uses GRID_STEP = 1.0
        deg, not 0.25 deg -- this was a deliberate size/time tradeoff (a
        0.25 deg grid over this region is ~100x240 = 24,000 points per day;
        at 30 animation frames that's 720k+ rows, too big to bake into a
        static JSON cheaply in the time available). If continuing this
        project, either (a) regrid but heavily subsample only for the map
        visualization while keeping 0.25 deg for the actual training data,
        or (b) move the grid to a proper backend/tile-based map (e.g.
        pre-rendered PNG heatmap tiles) instead of a scatter of raw points.
      - ACTION ITEM: implement real regridding with e.g. `xesmf` or
        `scipy.interpolate.griddata` / `xarray.interp` onto a proper
        0.25 x 0.25 deg lat/lon grid for both real sources, and change
        GRID_STEP to 0.25 in the synthetic generator too, for consistency.

  [MOSTLY DONE] 3. Input variables  (updated 2026-08-27: currents now real)
      - SST:  REAL data available and used (MOSDAC INSAT-3DR + CMEMS thetao).
      - SSS:  REAL data available and used (CMEMS `so`, file "Sea surface
              salinity.nc"). Wired into real_data.py / export_real_data.py /
              the dashboard's real-data trend chart (secondary y-axis).
      - Surface currents U,V:  REAL as of 2026-08-27. File
              cmems_mod_glo_phy-cur_anfc_0.083deg_P1D-m_....nc (uo, vo),
              same product family, 1-27 Aug 2026. Loaded by
              load_cmems_currents_series() in real_data.py: basin-mean
              speed series + a subsampled vector-field snapshot (lat, lon,
              speed, compass heading) for the most recent day. Rendered in
              the dashboard as an actual arrow/quiver map (Plotly marker
              symbol "arrow" with per-point `angle`), color = speed. This
              closes one of the two remaining input-variable gaps.
      - Chlorophyll (chl, phyc) -- BONUS, not one of the spec's 5 required
              inputs, but real data (CMEMS GLOBAL_ANALYSISFORECAST_BGC_001_028,
              0.25 deg, file cmems_mod_glo_bgc-pft_anfc_0.25deg_....nc) that
              ties to the problem statement's "marine ecosystems" framing.
              Loaded via the existing generalized load_cmems_series("chl").
              Shown as a real trend chart alongside currents.
      - SSH/SLA:            STILL NOT AVAILABLE. No file has been provided
                             for this. The synthetic pipeline invents a
                             plausible SSH field (smooth Gaussian "eddies")
                             purely for the thermocline-depth physics used
                             to generate synthetic subsurface temperatures --
                             it is NOT real altimetry data.
      - Surface winds U,V:      STILL only SYNTHETIC (a simple sinusoidal
                             wind-speed field in ocean_pipeline_demo.py). No
                             real wind product (e.g. ASCAT/OSCAT/ERA5) has
                             been integrated.
      - ACTION ITEM (only remaining input-variable gap): pull real SSH/SLA
        (CMEMS `zos`) and real winds (ASCAT/OSCAT via MOSDAC, or ERA5) for
        the same region/window if continuing. The `_find_cmems_dataset` /
        `load_cmems_series(varname)` pattern in real_data.py generalizes
        directly to `zos` the same way it did to `so`/`chl` -- just call
        `load_cmems_series("zos")` once the file exists. Winds/currents
        both being vector fields, load_cmems_currents_series() is a
        ready-made template for a load_cmems_winds_series() once a wind
        u/v file is available.

  [NOT DONE] 4. Compact satellite embeddings via DL (CNN/ViT/Autoencoder/GNN/
      attention)
      - THIS IS THE BIGGEST GAP. Nothing in this repo does representation
        learning or produces an embedding. The reconstruction model is a
        plain scikit-learn RandomForestRegressor taking raw tabular features
        (lat, lon, day, sst, ssh, sss, wind, one-hot cluster id) directly to
        depth-wise temperature -- no CNN/ViT/autoencoder/GNN, no latent
        embedding vector, nothing resembling "satellite embeddings".
      - The one nod to the recommended literature (Loo et al. 2026,
        arXiv:2605.00860, "Adaptive Spatiotemporal Clustering...") is a
        KMeans clustering step over (lat, lon, day, ssh) whose cluster id is
        fed into the RandomForest as a one-hot feature. This is a legitimate
        but very lightweight nod to the paper's idea, NOT an implementation
        of a deep embedding framework of any kind.
      - ACTION ITEM (highest priority for spec compliance): replace/augment
        the RandomForest with an actual DL model. Given the data actually on
        hand (gridded surface fields), a small CNN or convolutional
        autoencoder is the most tractable next step:
          (a) Stack available surface channels (SST, SSS, [SSH, winds,
              currents once available]) into a multi-channel image per day
              over the 0.25 deg grid.
          (b) Train a convolutional encoder (or a small autoencoder) to
              compress each day's multi-channel surface image into a
              compact latent vector per grid cell (or per patch) --
              this is the "satellite embedding".
          (c) Feed that embedding (instead of raw surface features) into a
              regression head (small MLP, or keep RandomForest as a
              baseline to compare against) that predicts the 15-level
              temperature profile.
          (d) Report both the embedding-based model's skill AND the
              RandomForest baseline's skill, so the value of the embedding
              step is demonstrated quantitatively (this satisfies the
              "evaluate... standard skill metrics" requirement AND makes
              the embedding step's contribution legible to judges).
        Framework suggestion given time constraints: PyTorch or a small
        Keras/TensorFlow model; either is fine, pick whichever the next
        session/dev is fastest in. Keep it SMALL (a few conv layers) --
        the point is to demonstrably satisfy the spec's architecture
        requirement, not to win a benchmark.

  [DONE, SYNTHETIC ONLY] 5. Train reconstruction model (surface -> profile)
      - RandomForestRegressor, multi-output (one model, 15 depth targets),
        trained on a time-ordered 75/25 split (no leakage), evaluated
        against a naive climatology baseline. This part works and is
        genuinely a valid ML training/eval loop -- it's just running on the
        synthetic dataset, and it's the wrong architecture class per the
        spec (see item 4).

  [DONE] 6. Standard depth levels
      - FIXED in this session: DEPTH_LEVELS in ocean_pipeline_demo.py now
        exactly matches the spec's list:
          [0, 5, 10, 20, 30, 50, 75, 100, 125, 150, 200, 300, 500, 700, 1000]
        (it was previously [50, 100, 200, 500], an arbitrary earlier choice).
        This propagates automatically through export_data.py -> data.json
        -> the dashboard (nothing else hardcodes the depth list). Re-run
        `python export_data.py` after this file if you change it again.
      - Caveat: these are still SYNTHETIC profiles (a physically-motivated
        but made-up thermocline curve), not GLORYS or real Argo temperature.

  [NOT DONE] Target dataset: GLORYS reanalysis / Gridded ARGO (INCOIS LAS)
      - Neither was integrated. The CMEMS files we have (thetao, so) are
        from `GLOBAL_ANALYSISFORECAST_PHY_001_024` (Mercator's real-time
        analysis/forecast system), which is a *sibling* product to GLORYS
        (GLORYS is the *reanalysis*, `GLOBAL_MULTIYEAR_PHY_001_030`) from
        the same CMEMS catalog/toolbox -- same access method, different
        `productId`/`datasetId` string. Also, critically, the files we have
        only carry ONE depth level (~0.49 m, i.e. essentially surface) --
        not a depth profile. To get an actual GLORYS temperature *profile*
        target, redo the CMEMS pull requesting `thetao` from
        `GLOBAL_MULTIYEAR_PHY_001_030` (or the analysis-forecast dataset)
        with a depth range covering the 15 standard levels, not just the
        surface. That single change (broaden the `depth` selection in the
        Copernicus Marine Toolbox request) would deliver real subsurface
        temperature targets and close most of the biggest remaining gap.
      - Gridded ARGO via INCOIS LAS was not attempted (no credentials/access
        set up; INCOIS LAS is typically a public THREDDS/OPeNDAP or web
        download, worth checking if it needs an account).
      - A raw (non-gridded) ARGO pull was attempted via `argopy` in this
        session: `pip install argopy` FAILED to build because one of its
        dependencies (`aiohttp`) has no prebuilt wheel for this machine's
        Python (3.14, very new -- aiohttp's C extension needs a compiler
        toolchain that isn't set up, or a matching wheel isn't published
        yet for 3.14). Fix options for next session: (a) use an older
        Python (3.11/3.12) via a separate venv just for the data-prep step,
        where `argopy` has prebuilt wheels, then export a CSV/Parquet for
        the main pipeline to consume; or (b) install build tools
        (`build-essential` / a C compiler) and retry; or (c) skip argopy
        entirely and hit the Argo GDAC's THREDDS/ERDDAP HTTP API directly
        with `requests` + manual NetCDF parsing (more code, no fragile
        dependency).

  [DONE, LIMITED] 7. Evaluation / skill metrics
      - RMSE per depth, model vs. climatology baseline: implemented and
